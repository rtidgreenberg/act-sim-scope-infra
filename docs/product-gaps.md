## 🟠 LP-1 — Instance State Consistency not integrated with Routing Service (or Persistence Service)
- **What it is:** ISC (`instance_state_consistency_kind`, RELIABILITY QoS; production in **Connext 7.3 LTS**) recovers a reader's instance-state transitions (DISPOSED / NOT_ALIVE_NO_WRITERS) after a disconnection, reconciling over an **internal builtin request/response channel** on rediscovery. Per RTI docs it is **"not fully integrated with the Infrastructure Services (Routing Service, Persistence Service, Web Integration, Recording)"**, and **"DataWriters and DataReaders communicating through Routing Service cannot communicate instance state consistency updates"** (an RS output writer can only *respond to* requests).
- **What does NOT work (and why):** anything that isn't a pair of genuine ISC-enabled matched endpoints. ✗ **RS** — its internal input-reader→output-writer forwarding doesn't carry ISC across. ✗ **RS Processor plugin** — runs inside that same RS data path, inherits the limitation. ✗ **Sidecar** (separate app publishing shadow state) — can't set a reader's real `instance_state`, only an app-level shadow.
- **What DOES work (our workaround):** a **standalone, ISC-enabled DP-to-DP relay** — standard `rti.connext` DomainParticipants with `instance_state_consistency_kind` **on both legs**, mirroring its reader's instance lifecycle (DISPOSED/NO_WRITERS → writer `dispose`/`unregister`). Native ISC runs **per leg** (source-writer↔relay-reader, relay-writer↔dest-reader), so true DDS `instance_state` converges end-to-end. No middleware-private state is touched externally — the relay only uses its **own** ISC endpoints. **Tradeoff:** state-critical topics **bypass RS** (you run this relay for them; RS still carries bulk traffic). Proven in **Roadmap Phase 1 (PoC)**, integrated in **Phase 8**.
- **Residual / to validate:** faithful **NO_WRITERS mirroring under partition** (relay-reader loses the source vs. source-writer truly gone); relay throughput for high-rate topics (scope it to low-rate keyed state topics).
- **Blocks:** nothing hard — **Phase 8 is achievable via the ISC relay** (validated first by the Phase 1 PoC). Cost is architectural (a parallel relay + bypassing RS for those topics) + the perf/scope caveat above.
- **Ask to RTI (softened but still valid):** integrate ISC with **Routing Service** (and PRS) so instance-state transitions propagate across the gateway — this would **remove the need to bypass RS with a custom relay**. Core-protocol + IS work → long lead; worth starting.
- **Source:** [What's New 7.3.0 — Instance State Consistency + Infrastructure Services limitation](https://community.rti.com/static/documentation/connext-dds/current/doc/manuals/connext_dds_professional/whats_new/whats_new/WhatsNew730.htm)

## 🟠 LP-2 — Persistence Service synchronization does not work through Routing Service
- **What it is:** PRS data-synchronization (redundant/transitive, anti-entropy, eventual consistency) is our intended **durable-state relay / "gossip overlay."** But: **"the data synchronization protocol does not work when there are Routing Service instances between the Persistence Service instances."**
- **Why it matters:** in the RS-per-node topology, a naive "PRS behind each RS" design is broken. Workaround: deploy each PRS as a **direct WAN-domain peer** (parallel to the RS plane, not routed through it) — viable, but it forces a parallel participant set and extra RF traffic, and isn't a clean routed-PRS story.
- **Blocks:** clean PRS integration in an RS-routed mesh — **Roadmap Phase 10 (v2 relay/durability)**. Not a hard blocker (overlay works).
- **Ask to RTI:** PRS-sync interoperation across RS-routed topologies. Medium lead.
- **Source:** [Synchronizing of Persistence Service Instances](https://community.rti.com/static/documentation/connext-dds/current/doc/manuals/connext_dds_professional/users_manual/users_manual/Synchronizing_of_Persistence_Service_Ins.htm)

## 🟠 LP-3 — RTPS Analyzer as a shippable, supported component (stable contract + robust decode)
- **What it is:** Scope depends on the **internal** RTPS Analyzer for the node graph + payload decode. To ship **Scope as a customer deliverable**, the Analyzer needs: a **stable, documented event/socket contract**; robust decode (**RTPS fragment reassembly** + XCDR1/2 from `act_types.xml` / TypeObject); and **productization/licensing**.

- **Blocks:** Scope as a **deliverable** (not the internal sim — the sim is fine without this). Business + engineering lead.
- **Ask to RTI:** decide Analyzer productization; publish a stable event contract; support the decode path (fragmentation + XTypes).
- **Source:** internal RTPS Analyzer repo review (this project, `references/`).

## 🟠 LP-5 — No API-level diagnosability for participant-partition mismatch; the log-based fallback has its own bugs
- **What it is:** when two DomainParticipants have non-overlapping participant-level `PARTITION` QoS, they go **fully mutually invisible** — `discovered_participants()` stays empty, no listener fires, no `StatusCondition` sets, nothing in `ParticipantBuiltinTopicData` explains why (confirmed empirically: `dir(dds.ParticipantBuiltinTopicData)` has no reason-code field, and a live mismatch produces zero API-visible signal on either side). The only diagnostic is Connext's internal middleware log at `STATUS_REMOTE`/`entities`-category verbosity, which emits a `PRESParticipant_hasMatchingPartition:UNMATCH` line naming both sides' actual partition strings as plain text — an operational log message, not a supported discovery API.
- **A second, independent bug in that same fallback message:** the `UNMATCH` line **swaps its own partition values relative to their GUID labels.** Verified with two participants on distinct concrete partitions (`AAA`/`BBB`) and both `instance_handle` GUIDs printed independently as ground truth: `A`'s real partition (`AAA`) is printed next to `B`'s GUID under "Remote DP," and `B`'s real partition (`BBB`) is printed next to `A`'s GUID under "local DP." The GUIDs themselves are correctly attributed (they match `instance_handle` and the RTPS frame prefix); only the two partition-string fields are transposed. Anyone building a monitor off this message without independently verifying GUID-to-partition attribution would silently produce a table with every entry's partition attributed to the wrong participant.
- **Why it matters:** a router/C2 roster feature ("what team is every mesh participant in right now?") has no supported API to build on. The only path is scraping an internal, undocumented, partition-swapped log message — fragile across Connext versions, and something we had to reverse-engineer by cross-checking against independently-known ground truth rather than trusting the message text.
- **What DOES work (our workaround):** a dedicated monitor combining **three** local-participant-scoped signals, joined by GUID: (1) `discovered_participants()` for peers that share its own partition (the matched half); (2) log-parsing of the (corrected-for-the-swap) `UNMATCH` line, scoped to `dds.Logger.instance.verbosity_by_category(LogCategory.entities, STATUS_REMOTE)` — **not** `LogCategory.discovery`, which emits zero `UNMATCH` lines despite this being nominally a discovery diagnostic — for peers it doesn't match, whose real partition string that line names; (3) a second, wildcard-partition (`["*"]`) sibling participant purely to resolve those GUIDs to real router identity (`participant_name`/`role_name`, D74/D79), since neither the log line (no identity field) nor `ParticipantBuiltinTopicData` (no partition field) carries both partition and name for an unmatched peer. Prototyped in `spikes/dp_partition_monitor/` (`partition_monitor.py`), stable across every run, verified to ~30-node scale.
- **Residual / to validate:** (1) a late-joining monitor takes up to ~30s (one SPDP re-announce period) to reach full coverage of already-existing mismatched peers — bounded, not permanent, but real; (2) a homegrown TTL for log-derived entries needs real margin (3x+) over that period or it flaps from ordinary timing jitter; (3) `dds.Logger.instance.output_handler(...)` left registered with raised verbosity segfaults the Python interpreter on normal process exit unless explicitly reset first (`reset_output_handler()` + drop verbosity) — reproduces with **zero** DomainParticipants involved, so any tool built on this must guarantee that reset on every exit path; (4) the `Logger` is **process-global**, not scoped to one local participant — in a process with several co-located DomainParticipants (the router's own shape: multiple WAN/LAN participants in one `router_main`), the handler receives `UNMATCH` lines for *any* two co-located participants' mismatches, including ones unrelated to the monitor, so it must filter by its own GUID (from `participant.instance_handle`, a different hex layout than the log's GUID format) or produce spurious/misattributed entries.
- **Blocks:** nothing hard — a roster/monitor feature is achievable via the workaround above. Cost is bespoke log-parsing infrastructure, a dedicated **standalone monitor process** (residuals 3+4 mean it should never be embedded in `router_main` itself — isolates the segfault-on-exit risk and the Logger's process-global blast radius from the router's critical path), plus the other residual risks above, none of which a supported API would require.
- **This is an API-exposure gap, not a missing protocol capability — the middleware already has the data.** The `UNMATCH` log line only exists because `PRESParticipant_hasMatchingPartition` already received and parsed the remote participant's real partition string and GUID in order to perform the match-check and log the result. Connext isn't declining to *discover* a non-matching participant at the protocol level — it discovers it, parses its declared partition, decides it doesn't match, and then withholds that already-in-hand data from every public, supported surface (`discovered_participants()`, `ParticipantBuiltinTopicData`, any listener/condition), leaking it only through an internal, undocumented, bug-carrying log message. The three-mechanism workaround above (and everything built on it, e.g. `docs/cpp_router/design-decisions.md` D88–D90) is explicitly an interim measure for this gap, not a permanent architecture choice — it should be revisited/retired if RTI ships the real fix.
- **Ask to RTI:** (1) expose the participant table Connext already builds internally — every participant it has discovered on the domain, matched or not, with its real partition set and identity — as a supported, queryable API (a builtin topic/reader, not a log scrape); a mismatch-reason field alone under-asks, since the actual product gap is "give us the full table you already parsed," not just "tell us why one entry is missing." (2) Fix the `UNMATCH` message's field-swap bug in the meantime, since it currently reports each side's own partition attached to the wrong GUID.
- **Source:** `spikes/spdp2_partition_visibility/`, `spikes/dp_partition_monitor/` (both incl. `PLAN.md`/`README.md`).

## 🟠 LP-6 — No supported per-sequence ACK/NACK attribution in protocol statistics
- **What it is:** Connext exposes useful writer/reader protocol statistics (`DataWriterProtocolStatus`, `DataReaderProtocolStatus`, and matched-endpoint variants), but those surfaces are aggregate snapshots and counters. They can report peer-scoped NACK counts, heartbeat counts, pushed/pulled samples, reader duplicates, uncommitted samples, and sequence-number boundaries such as first-unacknowledged / last-available / last-committed. They do **not** expose an event stream or queryable history that says "reader R ACKed/NACKed writer W sequence N" or "this NACK bitmap contained sequence N."
- **Why it matters:** our operator command log wants to explain whether a particular GUI command made it across the WAN and whether loss/repair affected that command. Aggregate protocol stats can say the peer path was healthy, lossy, repairing, or backed up during the command window, but they cannot prove command-level delivery or correlate one NACK/resend to one `command_id` without external packet decode or application-level correlation.
- **What DOES work (our workaround):** use application-level acknowledgement for command truth, keyed by a stable `command_id` / `request_id` carried through the routed command lifecycle. Keep protocol stats as contextual link telemetry beside the command row (NACKs, repairs, backlog, rediscovery), not as the authority for command success. If we need wire-level proof for investigations, capture/decode RTPS DATA/HEARTBEAT/ACKNACK/GAP by writer GUID/entity + sequence number using Analyzer/Wireshark-class tooling.
- **Residual / to validate:** exact RTPS sequence correlation requires capturing or instrumenting the command writer's sample identity and pairing it with packet-level observation; public protocol stats alone are insufficient. `wait_for_acknowledgments()` is only a writer-wide reliable-backlog barrier, not a per-command API unless writes are deliberately serialized, and even then it proves protocol acknowledgement rather than application execution.
- **Blocks:** exact per-command WAN delivery/protocol-forensics UI from protocol stats alone. It does **not** block a correct command UX if we add application-level command acknowledgements; it blocks using protocol stats as the sole proof source for "message X made it across."
- **Ask to RTI:** expose supported per-sample/per-sequence reliable-writer and reliable-reader acknowledgement/repair telemetry, at least keyed by writer GUID/entity, reader handle, and sequence number, or productize an Analyzer-grade supported API that emits DATA/ACKNACK/GAP/repair events with stable schemas. This would let operational tools correlate command IDs, DDS sample identities, and WAN repair behavior without relying on packet capture or internal analyzer contracts.
- **Source:** `docs/cpp_router/link-health.md`, `docs/cpp_router/design-decisions.md` D81/D82, current `ActRouterLinkStats` implementation; cross-checked with Connext AI guidance for 7.7.0 semantics.

## 🟡 LP-7 — User metadata on SPDP2 liveliness assertions and application callbacks on timeout
- **What we want:** obtain per-peer application-observed round-trip latency from independently scheduled RouterHealth samples, without triggering a reply or adding a dedicated periodic probe stream. Also provide a supported way to attach dynamic, application-defined user metadata (including router-health and timing records) to regular SPDP2 participant liveliness assertions, and notify the application when a remote participant's liveliness times out. Discovery/liveness and router health could then share **one periodic outbound message stream per participant** instead of separate periodic discovery, health, and RTT-probe streams.
- **Passive RTT design:** each outgoing sample carries, per peer, the peer incarnation/session ID, the last received heartbeat sequence, and the elapsed time from receiving that exact heartbeat to sending the outgoing sample (`reply_delay_ns`). The original sender retains its own monotonic send time for that sequence and computes `RTT = elapsed_since_original_send - remote_reply_delay` on receipt. Both nodes keep their independent publication schedules; the acknowledgment is piggybacked, not a triggered response. Only local elapsed durations are subtracted, so synchronized wall clocks and absolute timestamps are unnecessary.
- **Measurement semantics / safeguards:** correlate the exact acknowledged sequence and incarnation; bound retained send history; do not report a measurement when correlation is unavailable; deduplicate repeated acknowledgments. Measure the remote delay at actual send time as closely as the supported API permits. The result includes delivery/processing delays and combines a forward leg and a later return leg, potentially under different network conditions; it is not pure wire latency or an exact one-way measurement. Report measurement age and invalidate negative results rather than clamping them into apparently valid RTTs.
- **Ask to RTI:** expose supported send-time metadata population and receive-side access for dynamic, bounded metadata on **regular SPDP2 assertions**, including per-peer acknowledgment/timing records and compact router-health state. Specify payload limits, update visibility, scheduling/queueing semantics, security/access-control behavior, and interoperability with participants that do not consume the extension. The goal is one shared periodic assertion/health stream, not an extra periodic application topic or an immediate response for every received assertion. This does not require eliminating event-driven discovery, repair traffic, or per-destination packet copies.
- **Application callback contract requested:** notify the application when a remote participant's liveliness lease expires, identifying the participant/incarnation, the timeout reason, the last observed assertion time, and the effective lease duration. Distinguish timeout from graceful departure or administrative removal, and expose recovery when that peer becomes live again. The primary request is a **timeout/state-transition callback**, not a callback for every received assertion or a mandatory pre-send callback. Verify whether existing participant discovery notifications already provide this contract. Document callback threading, ordering, metadata ownership/lifetime, allowed API calls/reentrancy, and error handling; slow or failing application handlers must not stall middleware liveliness. Any health/RTT metadata access or timing hooks are a separate part of the request and must not require a reply or another periodic transmission.
- **What DOES work (implemented application-level option):** RouterHealth now carries per-peer acknowledgment/duration records, with monotonic send history and writer-incarnation correlation. This provides passive RTT without a dedicated RTT probe, but does not consolidate RouterHealth with SPDP2 assertions. See [D121](cpp_router/design-decisions.md#d121--passive-routerhealth-rtt-replaces-routerlinkprobe-2026-11-06-accepted).
- **Residual / to validate:** confirm whether the installed Connext version already supports dynamic user metadata on regular SPDP2 liveliness assertions and application-level participant timeout/recovery notifications with the required reason and identity information. Do not assume static participant metadata is refreshed on every assertion or that endpoint liveliness notifications are equivalent to participant lease expiration. Validate timeout/recovery behavior under loss and restarts, metadata freshness/reordering, callback overhead/failure behavior, bounded metadata size as peer count grows, and packet captures showing the consolidated periodic stream before claiming the one-stream goal is achieved. Participant lease timing must not silently replace the existing application health policy.
- **Blocks:** the bandwidth-minimal single-periodic-stream design; does not block application-level passive RTT using separate RouterHealth samples.
- **Source:** product request and design discussion, 2026-11-06; clarified 2026-11-11 to request application-defined user metadata and application-level liveliness timeout/recovery callbacks, rather than per-assertion callbacks. See the [RTI discovery guidance review and open questions](cpp_router/participant-discovery-performance-guidance.md). SPDP2 API support and wire behavior remain **verify-first**, not an established product limitation.

## 🟠 LP-8 — Finite-liveliness ISC recovery conflicts with full writer-side content filtering
- **What it is:** Connext 7.7.0 lists **infinite DataWriter liveliness** as a prerequisite for full writer-side ContentFilteredTopic (CFT) filtering. A finite writer liveliness lease breaks that prerequisite. The CFT remains functional with reader-side filtering; this is **not** a blanket incompatibility between ISC and CFT.
- **Why it matters:** our ISC spike demonstrated same-writer `NO_WRITERS → ALIVE` recovery after liveliness loss/regain, without another data sample. Using a finite lease to obtain that recovery conflicts with the sender-side filtering we need to avoid sending unwanted traffic over the radio. Separately, a router must translate a data-less upstream ALIVE recovery into a real downstream write; enabling ISC on both legs alone does not close that relay gap.
- **Current architectural choice:** retain infinite WAN writer liveliness and sender-side filtering; use application health messages/deadlines for system reachability, explicit dispose/NO_WRITERS forwarding for application lifecycle, and normal data publication for updates/revival. A health deadline miss is not a writer-liveliness loss and does not trigger the spike's ISC recovery path.
- **Residual / to validate:** silent instances across long outages and producer/router restarts still require explicit retention, replay, or producer-republication rules. More keyed instances do not make native ISC a persistence or restart-recovery solution. Do not treat ALIVE recovery as proof of fresh application data.
- **Blocks:** combining finite-writer-liveliness-driven ISC recovery with full writer-side filtering in the same WAN endpoint design. Does not block the current application-health/lifecycle approach.
- **Ask to RTI:** support full writer-side content filtering with finite writer liveliness and document its interaction with ISC, including data-less ALIVE recovery across routed endpoints, without requiring unwanted application data to cross the WAN.
- **Source:** [Connext 7.7.0 User's Manual, Chapter 45, writer-side filtering prerequisites](https://community.rti.com/static/documentation/connext-dds/7.7.0/doc/manuals/connext_dds_professional/users_manual/RTI_ConnextDDS_CoreLibraries_UsersManual.pdf) ("The DataWriter has infinite liveliness."); [native ISC and relay spike results](../spikes/isc_recovery/README.md); [current ISC design decision and findings](cpp_router/isc-findings.md). Added 2026-11-11.

### Qualification use case — instance churn across link outages

- **Execution plan and initial spike:** [instance churn and short-outage recovery](instance-churn-reconnect-test-plan.md) defines the deterministic workload, isolated test stages, measurements, and proposed acceptance budgets. The [implemented spike and initial results](../spikes/instance_churn_reconnect/README.md) show reliable Event catch-up after a 2-second outage but 41 best-effort Status ghosts in both the main native outage case and the production receive adapter's destination LAN, using schema version 3. Flow control can pace recovery; it cannot repair lost best-effort disposes. Complete qualification remains open.
- **Two-minute production-policy result:** unchanged reliable/volatile Event fails after a 120-second outage: **160 disposed contacts remain ALIVE** natively and on the destination LAN. Native instrumentation shows reliable readers become inactive at about 30.5 seconds and volatile history is removed despite a 300-second participant discovery lease and infinite writer liveliness. The never-disposed stationary contact remains ALIVE; actual health recovers independently. A longer reliable-reader retry budget and its memory/queue cost need a separate test, not a health/liveliness retune. [Detailed measurements](../spikes/instance_churn_reconnect/README.md#two-minute-outage-with-unchanged-production-qos-2026-11-11).
- **Requested workload:** 100 aggregate instance operations/sec across creation, updates, and explicit disposal combined, not 100 new instances/sec. Each active instance is updated every 2 seconds; those updates count toward the same 100 operations/sec budget. A 2-second outage therefore spans approximately 200 source operations, not necessarily 200 distinct instances or 200 WAN transmissions. Before running, specify the creation/update/disposal mix, active population, instance lifetime, and payload size; keep the population and update cadence consistent with the total operation budget.
- **Scenario:** establish delivery to the destination LAN, interrupt the WAN link for 2 seconds while producers continue creating/updating/disposing instances, then restore it without restarting writers or routers. Include previously received instances disposed during the outage, instances created and disposed entirely during the outage, surviving instances, and instances with several lifecycle transitions on the same key. Repeat across outage timing relative to the 2-second publication cycle.
- **Reliable Event expectation, to verify:** retained, unacknowledged data and lifecycle operations can catch up through ordinary reliable repair, without ISC. A burst of pending disposes is possible; it is not a special dispose-first snapshot. Older pending operations can delay newer traffic on the same writer. Retention/resource limits and reliable-reader inactivity handling bound this behavior; KEEP_ALL is not an unlimited outage guarantee. Verify actual destination state per key rather than assuming one application notification per historical operation.
- **Best-effort Status expectation, to verify:** there is no reliable backlog repair. Subsequent periodic samples can refresh surviving instances, but a dispose lost during the blackout is not guaranteed to be recovered. A previously received instance can remain stale unless an explicit cleanup/reconciliation mechanism removes it. KEEP_LAST(1) is per instance, not one latest sample for the entire topic, and does not guarantee delivery of missed deletions.
- **Measurements:** compare source truth with destination LAN state after recovery: live survivors, disposed instances, stale/ghost instances, missing survivors, and any older data that revives a deleted instance. Capture pending queue depth, blocking/errors, memory and retained instance counts, recovery bytes/rate, time to current-state convergence, and command/health latency during catch-up. Observe both adapter boundaries; WAN reception alone does not prove destination convergence. Health returning ALIVE does not prove application instances have converged.
- **Acceptance remains open:** define permissible convergence time, stale-instance lifetime, recovery bandwidth, resource usage, and command/health interference before declaring this gate passed. The measured cases above do not establish a general recovery guarantee. A separate restart/rediscovery case is required; outage tests do not qualify persistence.
- **Product question:** how can applications obtain bounded current-state/deletion convergence after instance churn and a short outage while retaining writer-side filtering, without an unbounded replay backlog or silently lost best-effort disposes? See [reliable delivery semantics](https://community.rti.com/static/documentation/connext-dds/7.7.0/doc/manuals/connext_dds_professional/users_manual/users_manual/Reliable_Delivery_Model.htm).

## Known constraints (workarounds exist / inherent — inform, don't block)

- ⚪ **C-1 — Monitoring Library 2.0 not in the host installer.** The node image must install the **target** monitoring package + set the lib search path. Packaging only; workaround known. *(Phase 4.)*
- ⚪ **C-2 — DDS Security defeats passive observation (inherent, not a bug).** Per-writer session keys reach only matched authorized readers, so a passive sniffer **cannot decrypt**; visibility degrades along the governance ladder. Not something RTI "fixes" — but **secured-network observability strategy** (an authorized-observer mode? Observability-based topology under security?) is a **product-strategy question** if Scope must work against secured customer networks. *(Phase 9.)*
- ⚪ **C-3 — RF-layer prioritization is ours, not RTI's.** EMANE RF Pipe is a flat single-queue pipe; prioritization must be enforced at the **DDS layer** (TransportPriority + flow controllers) or via `tc`/qdisc. No RTI ask. *(Phase 5.)*
